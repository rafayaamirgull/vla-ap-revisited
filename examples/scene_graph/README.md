# 3D scene graph from the wrist RGB-D camera

This step turns a MuJoCo wrist capture and its YOLO-World/SAM2 detection report into an instance graph in world coordinates. Each accepted object has a masked 3D point cloud, observed centroid and bounds, and a CLIP ViT-B/32 image embedding. The graph keeps pairwise metric measurements, directional and support edges, and ternary `between` relations separately so one object pair can have several valid relations at once.

## Run one frame

Use the Docker container and dependencies described in the [main README](../../README.md). Capture and process a **new** frame so the camera metadata and detection report contain RGB-D fingerprints:

```bash
docker exec vla_scenegraph_env /root/miniconda3/bin/python \
  /workspace/examples/ur5e_eye_in_hand/run.py --frames 1 --seed 7 --hb-count 3 \
  --output-dir /workspace/outputs/seed7_capture

docker exec vla_scenegraph_env /root/miniconda3/bin/python \
  /workspace/examples/open_vocab_pipeline/run.py \
  --input /workspace/outputs/seed7_capture/frame_0000_rgb.png \
  --prompts "red cube, green bell pepper, toy car" --confidence 0.005 \
  --output-dir /workspace/outputs/seed7_perception

docker exec vla_scenegraph_env /root/miniconda3/bin/python \
  /workspace/examples/scene_graph/run.py \
  --detections /workspace/outputs/seed7_perception/frame_0000_detections.json \
  --output-dir /workspace/outputs/seed7_graph
```

These separate directories keep the seed 7 capture from replacing the seed 1 RGB-D files referenced by the seed 1 perception report below. The first run of CLIP downloads its ViT-B/32 checkpoint into `/root/.cache/clip/` in the container. The [perception guide](../open_vocab_pipeline/README.md) shows how to keep this cache across container restarts. If HomebrewedDB is not mounted, the simulator captures only the cube and the graph still runs. A prompt that matches no visible object can produce zero detections.

Without explicit paths, the graph step reads `outputs/open_vocab_pipeline/frame_0000_detections.json` and writes these files under `outputs/scene_graph/`:

| File | Contents |
| --- | --- |
| `frame_0000_scene_graph.json` | Camera transform, provenance, nodes, pairwise geometry, binary edges, ternary relations, thresholds, and rejected detections. |
| `frame_0000_points.npz` | One world XYZ and RGB array per accepted instance. |
| `frame_0000_object_XX_clip_crop.png` | The image region used for that instance's CLIP embedding. |
| `frame_0000_scene_graph.png` | Observed 3D points, support graph, directed object-relation matrix with centroid distances, and `between` annotations. |

The JSON is schema version 2. Existing binary `edges` remain; `pairwise_geometry` and `ternary_relations` are separate arrays. Consumers of version 1 JSON should read the new `schema_version` before parsing and handle the additional relation types.

Process all detection reports in one directory with `--detections /workspace/outputs/open_vocab_pipeline --frames 0`. Use a separate `--output-dir` for each experiment: `frame_0000` names are reused by different captures, and rerunning into the same output directory replaces earlier results. `--no-plot` skips the PNG. Use `--device cpu` if CUDA is unavailable.

If you used the seed 1 prompt experiment in the [perception guide](../open_vocab_pipeline/README.md), pass its report explicitly. Its referenced `outputs/ur5e_eye_in_hand/frame_0000_*` RGB-D files must still be the original seed 1 capture; if they were overwritten, regenerate both the seed 1 capture and perception report first:

```bash
docker exec vla_scenegraph_env /root/miniconda3/bin/python \
  /workspace/examples/scene_graph/run.py \
  --detections /workspace/outputs/seed1_perception/frame_0000_detections.json \
  --output-dir /workspace/outputs/seed1_graph
```

## Geometry and frame convention

MuJoCo renders axial depth in meters. For a valid masked pixel `(u, v)` with depth `z`, the code uses the pixel center and camera intrinsics to form

```text
p_camera = [((u + 0.5) - cx) * z / fx,
            ((v + 0.5) - cy) * z / fy,
            z]

T_world_camera = T_world_base @ T_base_ee @ T_ee_camera_optical
p_world = T_world_camera @ [p_camera, 1]
```

The optical frame points right, down, and forward. The MuJoCo world frame is in meters. The tabletop's workspace convention treats world +X as right, +Y as front (away from the robot stand), and +Z as up. Directional edges use this fixed workspace convention, not the current wrist-camera view; moving the wrist does not reverse `left_of` and `right_of`. `T_world_base` matters because the UR5e base is translated and rotated in this scene. Each fresh capture records the full chain and the direct camera pose; the graph code checks that they agree. It also checks RGB, depth, and mask hashes before using them. Reports from older captures without the fingerprints must be regenerated by repeating capture and perception.

For each mask, invalid and out-of-range depth is discarded. Masks touching the image edge are excluded by default, including if they came from an older perception report; use `--allow-border-masks` to keep incomplete views. Points are grouped in metric voxels, connected within `--cluster-radius` (default 2.5 cm), and the largest component with at least `--min-points` (default 80) is retained. The point cloud is capped by `--max-pixels` (default 30,000) for clustering; the CLIP crop recovers full-resolution mask pixels that lie near the retained 3D component. Each node's bounds are the 2nd to 98th percentile of **observed** points, and its centroid is their coordinate-wise median. These are visible-surface measurements, not a full object shape or a 6D pose. Per-node mask, valid-depth, and image-border diagnostics describe what this wrist frame observed; they are not a percentage of the full object that is visible.

The graph keeps the detector's label as a prompt-conditioned candidate. It also compares the instance crop with every supplied text prompt and records CLIP's top prompt and its cosine margin over the runner-up. A margin below `--clip-margin` (default 0.04), or disagreement with the detector label, marks `semantic_status` as `ambiguous_within_prompts` and adds `?` in the plot. A larger margin only means the label is more distinct **among the supplied prompts**; it does not prove the physical object's identity. Include plausible alternatives in the prompt set.

## Relation categories and rules

| Category | Current output and evidence |
| --- | --- |
| Physical support | `object on support`: the observed object bottom is from 1 cm below to 2.5 cm above the support top, or at least 20 connected visible points lie from 1 cm below to 3 cm above the known table plane. Observed XY bounds must overlap by at least 30% of the smaller footprint. Object-to-object `on` additionally requires both observed Z bounds of the subject to exceed the target's matching bounds; the table contact-patch path does not require this ordering. The table support is known static MuJoCo geometry, marked as such in the graph. This is a geometric support hypothesis, not a measured contact force. |
| Containment | `object inside container` only when the object's observed bounds fit inside an explicitly supplied interior world AABB. |
| Proximity | Symmetric `object next_to object` when observed XY bounds are within 8 cm, median heights are similar, and they do not overlap or already have an `on` relation. |
| Metric geometry | Each unordered object pair has `centroid_delta_target_minus_source_world_m`, 3D and XY centroid distances, XY AABB clearance, XY overlap as a fraction of the smaller footprint, and 3D observed-AABB IoU in `pairwise_geometry`. Distances are in meters. These are visible-surface measurements, not a full 6D relative pose. |
| Directional ordering | `left_of` / `right_of` and `in_front_of` / `behind` use world X/Y observed-centroid differences greater than `--direction-deadband` (default 4 cm). `above` / `below` require separated observed Z intervals and at least `--vertical-xy-overlap` (default 0.15) of the smaller XY footprint. Each asserted direction has an inverse edge, explicit workspace frame, and measurement evidence. |
| Three-object ordering | `between` is stored in `ternary_relations` with one subject and two reference objects. The subject's XY centroid must project into the middle 15–85% of the anchor segment, lie within `--between-max-perpendicular` (default 6 cm) of that segment, and have a centroid height spread within `--between-max-height-spread` (default 12 cm). Anchors must be at least `--between-min-anchor-distance` (default 15 cm) apart. This is a planar ordering heuristic, not proof that the object blocks a path. |
| Visibility | Each node reports its wrist-frame visible mask pixel count, fraction with valid depth, and whether the mask touches the image border. The `occluded_fraction` field is `null` because the full object silhouette is unknown. This does not identify the object that caused an occlusion. |

The JSON permits multiple relation types for the same object pair; for example, one object can be both `left_of` and `in_front_of` another. The figure shows support, containment, and proximity as a compact graph. Its directed matrix shows every object-to-object relation and the 3D centroid distance, with the source in the row and target in the column; a separate callout shows ternary `between`. The JSON retains the complete evidence and metric values. X/Y directional order uses observed centroids, so partial masks and depth noise can move an edge across a threshold. Do not treat a direction edge as a calibrated probability.

The default tabletop scene has no calibrated container interior, so it normally emits no `inside` edge. To test a container, create a JSON file mapping a detected container ID to its measured **interior** bounds in world meters, then pass `--interiors /workspace/path/to/interiors.json`. Because object IDs are reassigned per frame, `--interiors` accepts only one selected detection report. For example, replace these illustrative numbers with the actual cavity bounds for the current frame:

```json
{
  "object_02": {"min": [0.20, 0.30, 0.27], "max": [0.36, 0.46, 0.38]}
}
```

Instance IDs are assigned per frame from detection order; there is no temporal tracking. A single wrist view cannot reliably reconstruct an unseen container interior, so `inside` is only asserted with this explicit prior. The connected contact patch helps recover support when an overhead view hides most of an object's bottom, but a SAM mask leaking onto the table could create a false contact patch. All inferred edges are geometric hypotheses with supporting measurements in the JSON. CLIP `text_cosine` values are similarities, not detection confidence. Check the YOLO/SAM overlay before treating low-confidence labels as research annotations.

### Relations that need more evidence

The current RGB-D frame does not assert `touching` or `attached_to`. A small visible gap is not enough to prove contact, and attachment is a mechanical state. MuJoCo contacts and equality/joint state could provide simulator-grounded labels for evaluation, explicitly marked as privileged simulator evidence. A deployable contact estimate would need a validated sensor or multi-frame contact model.

The graph likewise does not assert `occludes` or a percentage `partially_visible` from one segmented view: unseen shape cannot be recovered from that view alone. Camera-specific occlusion needs an amodal shape, another viewpoint, or simulator segmentation and depth for ground-truth evaluation. Border truncation is reported as an observation diagnostic. Reachability also depends on robot geometry and collision checking, not just camera visibility.

An action-linked statement such as “object inside drawer **after opening**” needs stable object IDs, an observed open/close state, an action record, and pre/post observations. It belongs in a temporal action graph with preconditions and effects rather than as a static edge from one frame. Full object orientation likewise needs pose estimation or a tracked 3D model; the current visible-surface AABB does not determine it.

### Using EmbodimentSemantic

The [EmbodimentSemantic paper](https://arxiv.org/html/2607.00020v1#S3) and [dataset card](https://huggingface.co/datasets/SemVLA/EmbodimentSemantic) are useful references for ordered triplets, inverse-direction checks, world-frame convention, and separate wrist/external views. Their published ontology has **eight** predicates: `is_left_of` / `is_right_of`, `is_in_front_of` / `is_behind`, `is_on_top_of` / `is_below_of`, and `is_inside` / `contains`. The linked work does not label `touching`, `attached_to`, `between`, `occludes`, metric geometry, or action effects. Our `on` and `inside` edges need a carefully defined mapping before comparing exact triplets with that benchmark; the dataset's simulator relations use different heuristics. The real SO101 scene graphs are VLM-generated and do not have physical-relation reference labels. The LIBERO HDF5 benchmark is the more relevant source for simulator-grounded triplet evaluation, and it is not required to run this example.
